# Repair Offline Storage and Synchronization

## What the audit found

- The service worker is generated by `vite-plugin-pwa`, registered at `/sw.js` with root scope, and intentionally disabled in Lovable preview/development. It can only be validated on a production/published origin.
- The current sync indicator can run forever by design: if any phase is incomplete it leaves the global state at `syncing` and restarts the whole pass every 20 seconds. The media phase requires all 1,324 exercise downloads to succeed, so one missing, blocked, or cross-origin response prevents completion indefinitely.
- Current data storage is fragmented across generic `idb-keyval` databases (`smarty-offline`, `smarty-offline-performance`, `smarty-offline-queue`, `smarty-offline-meta`). It does not expose real per-domain tables, per-table row counts, or per-table sync cursors.
- Member sync currently performs repeated full pulls for workouts, set logs, results, and feedback. It does not incrementally mirror all relevant user data, and it omits direct structured mirrors for questionnaires, generation sessions, workout plans, personal records, progress/badges, notifications, and support records.
- Some tables have `updated_at`, but append-oriented tables such as set logs, notifications, personal records, support messages, user badges, and workout plans only have creation/event timestamps. These need an explicit cursor strategy; existing server-generated rows should not be rewritten merely to fit a generic algorithm.
- Existing screens already have partial cache-first wrappers for workouts, logbook, progress, profile, account, and inbox. These can be redirected to a proper local repository without changing their UI.
- Session persistence is already configured correctly (`persistSession: true`, persistent browser storage, automatic refresh), and the protected route already falls back to the local session when offline. No auth-flow rewrite is needed.

## Implementation

1. **Stop the endless sync state**
   - Separate critical member-data sync from best-effort media/community warming.
   - End every sync run deterministically as success, partial success, or error; never hold `syncing` between retries.
   - Add request timeouts, bounded retries/backoff, cancellation on unmount, and single-flight locking.
   - Record per-phase outcomes and failed media counts instead of restarting the complete pass every 20 seconds.

2. **Create one explicit Dexie offline database**
   - Add Dexie and define stores for profiles, questionnaires, generation sessions, workout plans, workouts, set logs, workout results, workout feedback, personal records, notifications, support threads/messages, user progress/badges, relevant user community activity, sync metadata, and the outbox.
   - Scope every member row and sync cursor by user ID; keep public exercise/catalog data separate.
   - Migrate existing useful `idb-keyval` cached data and queued mutations without deleting it first, then retain compatibility reads during rollout.

3. **Implement incremental pull synchronization**
   - Pull authenticated rows through existing row-level access rules using `updated_at` where available and stable creation/event cursors where records are append-only.
   - Page every query, upsert transactionally, and advance a per-table cursor only after the whole page/pass commits.
   - Run after session restoration, on reconnection, foreground, and a restrained periodic interval while online.
   - Treat the backend as source of truth and use last-write-wins only where an actual mutable `updated_at` exists.

4. **Harden the outbox and multi-device reconciliation**
   - Move pending operations into a real Dexie outbox table while preserving existing action types and replay handlers.
   - Keep stable client IDs, bounded retries, failure details, and confirmed-write removal.
   - After a push succeeds, pull affected tables so changes created on one device converge on all others.
   - Preserve append-only workout attempts/set logs rather than applying unsafe record-level last-write-wins to them.

5. **Use local data first in existing authenticated screens**
   - Refactor only the shared fetch/cache layer and current loaders for Logbook, workout detail, Progress, Profile, Account, notifications, and conversations.
   - Render Dexie data immediately, reconcile online in the background, and preserve all current page structure, styling, business logic, and routes.

6. **Make the service worker reliable and deploy-safe**
   - Keep Workbox `generateSW`, root scope, production/preview guards, and automatic updates.
   - Precache the compiled shell and use a navigation fallback excluding API/OAuth paths.
   - Cache stable public routes cache-first with background refresh; keep authenticated navigations network-first with last-good offline fallback.
   - Keep hashed assets cache-first and report registration, activation, scope, controller status, and cache byte/count diagnostics.

7. **Download media without blocking core sync**
   - Download the 1,324 exercise media files in resumable batches with timeouts and persisted progress.
   - Count stored bytes and successful/failed objects; failed files retry later without keeping the global status active.
   - Request persistent browser storage and report whether it was granted.

8. **Upgrade the hidden diagnostics route**
   - Extend `/diagnostics` with worker scope/controller details, Cache Storage names/counts/estimated bytes, Dexie table names and row counts, per-table last sync timestamps/cursors, outbox status, media progress, quota/usage, and the last sync outcome/error.
   - Keep it internal/noindex and expose no tokens or personal record contents.

9. **Database support and verification**
   - Add only the minimal timestamp/index migration needed for mutable user tables that cannot currently support reliable incremental sync; preserve RLS and grants.
   - Add unit tests for cursor advancement, last-write-wins, outbox replay, partial media failure, and sync-state termination.
   - Verify production build output contains `/sw.js` and its precache manifest, then test a published-origin-equivalent production server: worker controls the page after reload, data/media counts grow, sync returns to idle, and cached routes/data reopen with network disabled.

## Expected verification after implementation

- DevTools → Application → Service Workers: one active `/sw.js`, scope `/`, and the page controlled after the first reload.
- IndexedDB: one `smarty-workout-offline` database with named domain tables, non-zero row counts for the signed-in account, per-table sync metadata, and an empty outbox after successful upload.
- Cache Storage: versioned shell/assets/public-page caches plus a media cache. With all 1,324 exercise files available, storage should normally be tens to hundreds of MB depending on GIF sizes—not a few KB. Diagnostics will show the exact byte estimate and stored media count for the device.
- The status pill returns to idle after core records finish; partial media failures are visible in diagnostics and retry later without an endless spinner.
